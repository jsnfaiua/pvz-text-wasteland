1. **零差异门槛**（§5.1）：新功能从设计起就必须单机 / 联机 host / 联机 guest 表现一致，禁止"单机先行、联机后补"。

6. **dev 可测**（§13.14）：每项功能必须有 F9 面板入口或在 `wdev.js` 注释里写明用哪个现有入口测。
7. **行数统计**（§13.13）：每个迭代结束跑 `node dev-tools/count-lines.mjs`，提交说明记录增减。

### A1 室内箱建筑类型混合字池 ⬜

**状态** ⬜ ｜ **规模** S ｜ **触及红线** 无（纯掉落逻辑，需过 §5.1 零差异）

**问题现状**
`wdistrict.js:19-33` 的 `BUILDING_TYPES` 13 种建筑各自定义了 `glyphBias`
（`supply` / `medical` / `archive` / `material` / `car` / `weapon`），
但**全库没有任何代码读取该字段**（仅定义处出现）。
室内开箱时 `survival.js:2754` 仍只按瓦片类型硬映射四种来源：

```text
WBOX → weapon    MEDBOX → medical    MATBOX → material    其余 → supply
```

后果：**医院和仓库里的同款物资箱掉落完全相同**，建筑分型只影响了基础物资（`loot` 字段），
没有影响文字掉落。统一开发文档 §4.11 的 🟡「室内箱目前使用通用室内概率及默认物资字符池，
建筑类型混合池尚未接入」正是此项。

**设计方案**

1. **新增 `archive` 字符池**：`GLYPH_SOURCE_POOLS` 现有 5 池（supply / weapon / medical / material / car），
   缺 `glyphBias: 'archive'` 对应的池（学校 / 图书馆 / 档案室 / 印刷设施共 4 种建筑都指向它）。
   档案池字符方向：字、名、词、典、书、页、纸、印、册、录、档、案、文、楔、净、缺。
   权重和必须 = 1（§13.6），补 smoke 断言 `balance:GLYPH_SOURCE_POOLS.archive`。
2. **混合比例定案**（新增 `wbalance.js` 常量 `INTERIOR_GLYPH_MIX`）：
   室内箱字池 = 瓦片类型池 × 60% + 建筑 glyphBias 池 × 40%。
   理由：既保留"医疗箱主要出医疗字"的直觉，又让"医院的建材箱也带点医疗字"体现建筑主题。
   40% 为初始值，实测手感后可调；混合实现为纯函数 `mixGlyphPools(poolA, poolB, ratio)`
   放 `wwordcraft-rules.js`，输出权重和仍 = 1。
3. **接线点**：`openInteriorBox`（`survival.js:2678`）已经能拿到 `sv.interior.buildingType`
   （`windoor.js:407` 已存字段），把 glyphBias 池通过 `rollWordAddon` 的 `options.glyphPool` 传下去。
   室外箱不受影响（无建筑归属）。
4. **字楔来源同步**：`WEDGE_SOURCE_TABLES` 已有 `interior` 行，档案类建筑应偏向 clean/stable
   （文档 §9.2「档案室/印刷设施：字楔、词典、清晰字」）。新增 `archive` 行：
   rough .30 / stable .40 / clean .25 / infected .05。

**验收标准**
- 医院室内箱开出的医疗字占比显著高于仓库室内箱（1000 次抽样可统计验证）。
- 档案类建筑能开出 `archive` 池独有字符（字/词/典/楔等），其它建筑开不出。
- 各池权重和 = 1；室外箱掉落分布与改动前完全一致（无回归）。

**验证命令** `node dev-tools/smoke-test.js`（新增 archive 池权重和 + 混合函数断言 + 分布抽样）

**dev 入口** F9 面板新增「掉落追踪」：显示本次开箱的 来源 / 建筑类型 / 混合后池名 / 命中字符
（同时满足 §4.10「调试模式必须能显示：来源、基础概率、修正项、最终概率、随机值和命中结果」）。

### A2 楼层掉落修正真正触发 ⬜

**状态** ⬜ ｜ **规模** S ｜ **触及红线** 无

**问题现状**
`wbalance.js:299-306` 的 `WORD_LOOT_REGION_MODIFIERS` 已配好 6 行修正，其中
`underground1`（none −0.05）与 `underground2`（none −0.08、complete +0.01）**永不触发**：
`wordRegionModifier()`（`survival.js:2762`）只用 `districtAt()` 返回的区域键
（urban / suburb / wild / ruins），从不读 `sv.interior.floor`。
统一开发文档 §4.11 的 ⬜「地下1层/2层修正已配置，但当前室内框架没有楼层状态，尚未触发」
——**该前提已过时**：`windoor.js:406` 早已有 `floor` 字段、`FLOOR_BASEMENT_TYPES`
（`wbalance.js:543`）也已定义地下层建筑类型。纯粹是没接。

**设计方案**

1. `wordRegionModifier(gx, gy)` 增加可选 floor 参数：
   `floor === -1 → underground1`、`floor <= -2 → underground2`，地上层沿用区域修正。
   楼层修正与区域修正**取楼层优先**（不叠加），避免"废墟地下 2 层"概率溢出到负值/超 1。
2. **地上高层也应有修正**（文档 §9.3「更深楼层提高僵尸数量、生命和掉落品质」当前只做了
   僵尸缩放，掉落品质只在地下 +1 档）：新增 `upstairs2` / `upstairs3` 两行轻修正
   （none −0.02 / −0.03，glyph +0.01 / +0.02），让"爬到顶楼"有额外回报。
3. **修正后必须归一化**：新增纯函数 `normalizeProbTable(table)`，任何 modifier 叠加后
   重新归一到和 = 1 并裁掉负值。这是现有 `applyProbabilityModifiers`
   （`wwordcraft-rules.js:273`）缺失的保护——目前修正后不做归一，多个修正叠加可能溢出。
4. 楼层修正键值同步进统一开发文档 §4.8 表格。

**验收标准**
- 地下 2 层箱子的「无文字结果」率明显低于 1 层（1000 次抽样可验证）。
- 任意修正组合后概率表和 = 1、无负值（smoke 断言覆盖极端叠加）。
- 地上 1 层掉落分布与改动前一致（无回归）。

**验证命令** `node dev-tools/smoke-test.js` + `node dev-tools/full-run-test.mjs`（floors 覆盖室内路径）

**dev 入口** F9 已有楼层跳转（`wdev.js` 引 `windoor.js`）；配合 A1 的掉落追踪显示当前 floor 修正键。

### A3 缺字补偿池与连续保底 ⬜

**状态** ⬜ ｜ **规模** M ｜ **触及红线** §4 序列化（保底计数需存档）

**问题现状**
全库 0 处补偿 / pity 逻辑（grep `缺字补偿|保底|pity` 仅命中无关的射程衰减注释）。
统一开发文档 §4.11 与路线图 P0 均挂 ⬜「缺字补偿池、连续8次保底和调试界面概率追踪尚未开发」。
当前玩家可能连续几十次开箱都拿不到配方缺的那一个字 —— 这是掉落系统**最大的挫败感来源**，
且与本模组核心资源抉择（"有限字楔优先让什么成为现实"）直接冲突：玩家卡在缺字上，
根本走不到抉择环节。

**设计方案**

1. **补偿触发条件**：连续 N 次文字掉落判定（含"无文字结果"）都没有产出"玩家当前缺的字"
   → 下一次强制从缺字补偿池抽取。N 初始值 = 8（沿用文档定案），进 `wbalance.js`
   常量 `GLYPH_PITY_THRESHOLD`。
2. **"玩家当前缺的字"定义**（关键设计，避免不可预测）：
   取**已解锁配方**中"只差 1~2 个字符即可制作"的配方所缺字符，构成补偿池。
   若没有任何配方接近可做（比如刚开局背包空），则补偿池 = 当前来源池，即退化为普通抽取，
   计数不清零（不浪费保底）。这条保证补偿始终**指向玩家真实卡点**，而不是随机送字。
3. **计数器归属与序列化**：
   - 计数器 `sv.glyphPity`（整数）必须进 `wstate.js` 白名单 + 迁移表（缺省 0）。
   - **联机 host 权威**：掉落由 host 生成（§6），计数器归 host；guest 不本地维护，
     随 wsync 只读同步显示。**多人共享同一计数器还是各自独立？** → 定案：
     **各玩家独立**（`sv.glyphPity` 存在角色档、随 guestHp 同类字段单播），
     否则 A 的保底被 B 消耗，体验诡异。
4. **难度联动**（§13.7）：`DIFF_TABLE` hardcore ×1.5 → 硬核模式阈值放宽到 12 次
   （更难触发保底）。文档 §14 待定项「缺字补偿连续8次触发阈值是否应按难度模式调整」
   → 本方案定案为**按难度调整**，正常 8 / 硬核 12。
5. **反馈可见**：触发补偿时 `pushMsg` 提示（如"残页在手中拼合出你需要的字"，暖色），
   让玩家感知到系统在兜底，而不是默默给字。

**验收标准**
- 构造"只差 1 字"场景，连续开箱 8 次内必得该字（100 次重复实验 100% 命中）。
- 无接近可做配方时不触发、计数不清零。
- 硬核难度阈值 = 12。
- 计数器存档往返不丢；联机双端各自独立且不互相消耗。

**验证命令** `node dev-tools/smoke-test.js`（保底纯函数断言 + 阈值 + 难度映射）
+ `node dev-tools/full-run-test.mjs`（存档往返）+ 双端 CDP 实测（`_cdp-mp-real.mjs`）

**dev 入口** F9 面板新增「保底计数」显示 + 一键设为阈值−1（直接验证下一次必触发）。

### A4 低动态设置：减少闪烁 / 降低侵蚀特效 ⬜

**状态** ⬜ ｜ **规模** S ｜ **触及红线** §7 性能（关闭特效应降低开销，不得反向增加）

**问题现状**
仅 `wwordcraft.js:64` 读了系统 `prefers-reduced-motion`，`style.css:2673` 有一条媒体查询；
**没有游戏内开关**。统一开发文档 §2.1、§8.3、§10.4、§11.2 四处都要求提供该选项，
且 §10.4 已写好完整降级规范。这既是可访问性缺口，也是低配机器的性能出口。

**设计方案**

1. **两个独立开关**（文档 §10.4 明确区分，不要合并成一个）：
   - `减少闪烁`：闪烁改为明暗缓变 + 轮廓偏移 + 静态裂隙，不再高频切换。
   - `降低侵蚀特效`：减少字符密度、错位幅度、粒子数量。
2. **存储位置**：属于**玩家偏好**而非世界状态 → 存 `saveData` / profile，
   **不进 wstate 世界档、不进 wsync**（与 `_devHud` 同类处理）。联机各端本地独立生效
   —— 这是零差异原则的合法例外（可访问性偏好本就应各端独立），需在文档明确记录。
3. **默认值**：跟随系统 `prefers-reduced-motion`（首次进入时初始化），之后以玩家手动设置为准。
4. **接入点**：`render.js` 侵蚀渲染路径读取开关，走"参数化强度"而非分支复制代码
   （避免两套渲染逻辑）。强度常量进 `wbalance.js`（`INF_VIS_LOW_MOTION`）。
5. **UI 位置**：本体设置面板（`ui/settings.js`）荒原区块，或荒原局内 ESC 菜单；
   必须纯键盘可达（§13.11）。

**验收标准**
- 两开关可独立切换、跨局持久化。
- 开启后侵蚀渲染帧耗时**不高于**关闭时（CDP 实测 61fps 零长帧）。
- 感染进度仍可读（§10.4：字符错位应保留原角色轮廓）。

**验证命令** `node dev-tools/_cdp-perf.mjs`（开/关两轮五场景 FPS 对比）+ 截图人工确认

**dev 入口** F9 面板加两个开关的快捷切换（便于对比截图）。

### B2 字块元数据四维（来源 / 清晰度 / 污染度 / 字性） ⬜


**状态** ⬜ ｜ **规模** L ｜ **触及红线** §4 序列化（**高危**：动背包物品结构）

**问题现状**
统一开发文档 §5.1 属性目标表里，除「字符」「数量」两项 ✅ 外，
**来源 / 清晰度 / 污染度 / 字性 / 现实重量 / 耐久 全部 ⬜**。
代码里字块就是裸字符串 `glyph:汉字`（`wwordcraft-rules.js:151`），
唯一的额外维度是污染度（`glyphId(char, pollution)` 已支持 clean/unstable/infected，
`ZOMBIE_POLLUTION_TABLES` 已配）。
这是文档 P1 主线，也是 B3 相容线反馈、D3 字楔生命周期的**共同前置**。

**设计方案（分三个子任务，可分批上线）**

**B2-a 结构改造（先做，不加新玩法）**
- 字块 id 从 `glyph:字` 扩展为 `glyph:字:<元数据编码>`，或改为对象化槽位。
  **推荐后者**：物品带 `meta` 字段，避免 id 字符串无限膨胀、也便于 UI 展开。
- **堆叠规则定案**：元数据**完全相同**才堆叠；不同来源的同一个字**分开堆叠**。
  背包默认按字符折叠显示（§11.2「字块背包默认按字符堆叠，可展开查看来源、清晰度、污染度和耐久」），
  展开才看到分组明细。这是 UI 层的关键设计，必须与 `panel.js` 一起改。
- **旧档迁移**：历史 `glyph:字` 视为 `来源=未知 / 清晰度=完整 / 污染=纯净 / 字性=未定`，
  由 `buildRun` 自动补齐（§4：禁止跳过迁移直接改读法）。迁移表必须更新。

**B2-b 四维取值与产出规则**
- **来源** = 抽取时所在容器 / 僵尸职业（自然、工业、医疗、人体、档案、感染区，6 类，
  与现有 5 池 + archive 池对齐）。
- **清晰度**（完整 / 磨损 / 残缺）：按区域与楼层决定概率 —— 废墟 / 深层出磨损残缺多，
  档案类建筑出完整多。**功能影响**：磨损增加具现耗时、残缺增加失败或需更高字楔。
- **污染度**（纯净 / 不稳 / 感染）：**已有实现**，本项只是纳入统一 meta 结构。
- **字性**（主体 / 用途 / 材料 / 形态）：**这是纯规则映射，不是随机** ——
  每个字符在字典里固定属于某一字性（"枪"=主体、"药"=用途、"木"=材料、"块"=形态）。
  需要给全部现有字符池建一张 `GLYPH_NATURE` 表。字性用于 B3 的相容判定。
- **现实重量 / 耐久** ⏸️ 暂缓：这两项与 D3 字楔生命周期强耦合，本项先不做，
  只在结构上预留字段。

**B2-c 配方消耗规则**
- 配方检查从"有这个字"升级为"有满足条件的这个字"：
  基础配方接受任意清晰度，高级配方（枪械 / 精密设备）要求"完整"清晰度。
- 消耗时**优先用最差的合规字块**（自动节省好字块），玩家可手动指定；
  §11.2 要求的"锁定稀有字块、防止自动填入"一并做。

**验收标准**
- 新档字块带完整四维、可在背包展开查看；旧档字块正常显示为"未知来源/完整/纯净"。
- 同字不同来源分开堆叠、折叠视图正确合并计数。
- 配方按清晰度门槛正确校验；锁定的字块不被自动填入。
- 存档往返、联机双端背包一致。

**验证命令** `node dev-tools/smoke-test.js`（meta 编解码 / 堆叠 / GLYPH_NATURE 全覆盖 / 配方门槛）
+ `full-run-test.mjs`（多 seed 存档往返）+ 双端 CDP 实测背包一致性

**dev 入口** F9「给字块」支持指定四维（来源/清晰度/污染/字性任选），
用于直接构造 B3 相容测试所需的极端组合。

**风险提示**：本项动背包物品结构 = 触碰 §4 红线区。开发前必须完整审计
`panel.js` / `wwordcraft.js` / `wstate.js` / 所有 `glyph:` 消费点，
并**先写迁移测试再改结构**。这是本清单中回归风险最高的一项。

### B3 相容线与风险提示 ⬜

**状态** ⬜ ｜ **规模** M ｜ **依赖** B2（字性 + 污染度）｜ **触及红线** 无（纯 UI + 规则）

**问题现状**
统一开发文档 §5.2 已定案完整的五种反馈（白色实线 / 黄色抖动线 / 红色断线 / 黑色渗字 / 无反应），
且明确要求「必须同时使用颜色、线型、图标和动画，不能只依赖颜色」（可访问性）。
当前拼字台只显示"缺哪些字"，**没有任何相容性可视化** —— 玩家无法在投入字楔前
预判"这个组合会不会出问题"，与文档 §6.3「畸变风险必须提前提示」冲突。

**设计方案**

1. **相容判定纯函数**（进 `wwordcraft-rules.js`，供 UI 与 smoke 共用）：
   `evalCompatibility(recipe, slottedGlyphs, wedge)` → 返回逐连接点的等级
   （stable / degraded / invalid / forced / none）+ 原因码。
2. **五级判定规则定案**：
   - **白色实线 stable**：字符正确 + 清晰度达标 + 纯净 + 字性符合配方槽位要求。
   - **黄色抖动线 degraded**：可连接但品质下降 —— 清晰度为"磨损"，或字楔等级
     刚好够用无余量。结果：成品耐久 / 品质降档（具体降幅进 `wbalance.js`）。
   - **红色断线 invalid**：字符错误 / 字性与槽位冲突 / 字楔等级不足 → 禁止开始具现。
   - **黑色渗字 forced**：使用不稳 / 感染字块或（未来的）感染字楔强行连接 →
     可以开始，但必然带污染风险，需二次确认。
   - **无反应 none**：词义不存在 / 字序错误 / 概念未解锁（对应文档"世界不会承认任意组合"）。
3. **四通道表达**（不只靠颜色）：颜色 + 线型（实线/虚线/断线/渗染）+ 图标（✓ / ! / ✕ / ☠）
   + 动画（静止 / 抖动 / 断裂 / 渗流）。开启 A4「减少闪烁」时动画降级为静态图标 + 明暗缓变。
4. **风险二次确认**：forced 级别必须弹确认（明示可能后果），
   满足文档 §8.2「畸变风险必须提前提示，不能无提示摧毁玩家的重要资源」。
5. **原因码文案**（§13.5）：每个原因码对应一句具名文案，禁止散落字面量。

**验收标准**
- 五种等级都能在拼字台复现（配合 dev 构造极端组合）。
- 判定纯函数无 DOM 依赖、smoke 可断言全部分支。
- 红色断线时无法开始具现；黑色渗字必须二次确认。
- 减少闪烁开启后仍可区分五种等级（截图人工确认）。

**验证命令** `node dev-tools/smoke-test.js`（五级分支 + 原因码全覆盖）+ CDP 截图五态

**dev 入口** F9「给字块」构造各等级所需组合（依赖 B2 的 dev 入口）。

## 二·E 地图系统（新增大系统）⬜

> **总体定位**：荒原是**无限程序生成世界**（`render.js:3`「无限地图：镜头跟随玩家，
> 地块按需向 world.js 查询，坐标可正可负」），玩家目前**完全没有任何地图**——
> 只能靠记忆和紫菱形距离指引找营地。这在无限世界里是重大导航缺失：
> 走出去 40 格就不知道怎么回家，探索半径被"怕迷路"心理限制住了。
>
> **设计总原则**：
> 1. **地图是搜集来的知识，不是天赋**。无限世界不能一开局给全图（既剧透又违背末世感），
>    必须"走过才有"。这同时天然解决了无限世界的存储问题。
> 2. **不引入新的真相源**。地图只是 `world.js` 已有确定性生成结果的**可视化投影** +
>    一层"是否探索过"的位掩码。地形数据绝不复制存档（seed 已能重算）。
> 3. **存档体积是硬约束**。已知 localStorage 5MB 配额风险（曾在旧清单 P1-1 预警，
>    `flushSave` 超 3MB 会告警）。探索记录必须用**区块级位掩码**而非格级。

### E1 世界地图框架（探索记忆 + 全屏地图）⬜

**状态** ⬜ ｜ **规模** M ｜ **触及红线** §4 序列化（**新存档字段，需控体积**）+ §7 性能

**问题现状**
- 全库无任何 minimap / 地图 UI（grep `minimap|小地图` 仅命中 `Map()` 数据结构）。
- 唯一导航辅助是营地方向的紫菱形指引（8/7 加的距离指引）。
- 世界是 `CHUNK` 分块无限生成（`wdistrict.js:50` `CITY_SPACING = 52`，
  城市中心按 52 区块间距分布），玩家**没有任何手段知道下一座城在哪个方向**。

**设计方案**

1. **探索记录粒度 = 区块（chunk）**，不是格。
   - 玩家所在区块及其 8 邻域标记为"已探索"（走过即记）。
   - 存储结构：`sv.mods.explored`，键为 `'cx,cy'`，值为 1。
     每个区块 1 个键 ≈ 10 字节；探索 2000 个区块 ≈ 20KB —— 对 3MB 预算无压力。
   - **绝不存地形**：打开地图时按 `world.seed` 现场重算该区块的区域类型 / 城市中心 /
     路网（全是已有的确定性纯函数：`districtAt` / `cityCenterAt` / `arterialInfoAt`），
     只用 explored 决定"画还是不画"。这是本设计的核心——**零地形存储成本**。
2. **地图呈现层级**（一张图两个缩放档，不做多级地图）：
   - **区域视图**（默认）：1 区块 = 1~2 像素，显示区域配色
     （城区 / 郊区 / 荒野 / 废墟）+ 城市中心图标 + 主干道线 + 营地 / 玩家位置。
     未探索区块画成"未知底色"（暗墨绿噪点，符合 §10.3 世界色彩方向）。
   - **局部视图**（放大）：1 区块 = 8~12 像素，额外显示已发现的建筑门 / 车辆 /
     已清剿标记。
3. **渲染实现**（§7 性能硬约束）：
   - 地图**不进主循环**：打开时一次性绘制到离屏 canvas，之后只重绘玩家光标。
     关闭即释放。绝不逐帧重算区块。
   - 绘制预算：一屏最多绘制 N 个区块（超出按缩放合并），
     首次打开耗时目标 < 100ms（与驾驶 BFS 首建 6000 格预算同量级思路）。
4. **交互**（§13.11 键盘全覆盖）：
   - `M` 键开关（**当前 M 键未被占用**——已核对 `survival.js:4677` 的按键表：
     w/a/s/d/空格/f/b/j/escape/p/r/v/g/q/e/x/h/f1/f9/f11 + 方向键，M 空闲）。
   - 地图打开时：方向键 / WASD 平移视图，`+/-` 或 `Q/E` 缩放，`Enter` 居中到玩家，
     `M`/`ESC` 关闭。**世界必须暂停或保持安全**——参照搜索界面的处理
     （`survival.js:4764` 搜索界面打开时世界不暂停、角色仍可走位逃生）。
     **定案**：地图打开时世界**继续运行但玩家不能移动** → 危险；
     改为**地图打开即暂停**（单机），联机走已有的双向暂停同步（§6 教训 8）。
5. **序列化与联机**：
   - `sv.mods.explored` 进 `wstate.js` 白名单 + 迁移表（缺省 `{}`）。
   - **归属定案**：探索记录属**世界档**（`wasteland_world_<seed>`，host 权威），
     理由——同一世界两人一起探索，地图应共享（"我们一起摸清了这座城"）；
     若归角色档，guest 换角色就丢图、且双端地图不一致。
   - 双向同步：guest 走过的区块必须上报（参照 `wdiff` 改地的双向机制），
     否则 host 存档缺 guest 的探索（§6 教训 2：guest 端发起的变更必须上报回传）。

**验收标准**
- 走过的区块在地图上显示、未走过的是未知底色；跨局持久。
- 地图能看出城市中心与主干道走向，可用于导航（人工可用性确认）。
- 打开地图首帧 < 100ms、关闭后主循环帧率无回归（CDP 61fps 零长帧）。
- 探索 2000 区块时世界档增量 < 50KB。
- 联机：guest 探索的区块 host 端地图也可见，双端地图一致。

**验证命令** `smoke-test.js`（explored 编解码 + 区块标记纯函数）
+ `full-run-test.mjs`（存档往返 + 体积断言）+ `_cdp-perf.mjs` + `_cdp-mp-real.mjs`

**dev 入口** F9 新增「揭示全部地图（半径 N 区块）」+「清空探索记录」，
免得每次测地图都要跑几千格。

## 二·F 食物系统（新增大系统）⬜

> **总体定位**：当前食物系统是**单一物品 + 两个数字**——
> `panel.js:17` 的 `food: { heal: 30, satiate: 30 }` 和 `herb: { heal: 15, satiate: 12 }`，
> 全世界所有食物来源（`survival.js` 6 处 `return ['food', n]`）都产出同一个 `'food'`。
> 玩家吃什么都一样，"找吃的"这个末世核心行为**没有任何决策深度**。
>
> **已有可复用基础（重要，不要重造）**：
> - 饱食 / 水分双条：`HUNGER_MAX/DRAIN/LOW/STARVE_*`、`WATER_MAX/DRAIN/LOW/DEHYDRATE_*`
>   （`wbalance.js:464-479`），含奔跑额外消耗、低值减速、归零掉血 —— 框架完整。
> - 疾病系统：`SICKNESS`（`wbalance.js:622-627`）已有 感冒/伤口感染/**食物中毒**/痢疾/中暑
>   5 种，含每小时流失、治愈条件、6 种对应药品（`SICK_MED`）。
>   **食物中毒已存在**（`SICK_POISON_CHANCE = 0.06`，挨饿时触发）—— 吃坏东西中毒的
>   通路已经通了，食物系统只需接上"什么食物会导致中毒"。
> - 体质与天赋：`TALENTS.ironstomach`（铁胃：食物中毒免疫）、
>   `CONGENITAL.diabetes`（糖尿病：饱食消耗 +30%）—— **食物相关天赋已埋好**，
>   现在这两个天赋因为食物无差异而几乎没意义，食物系统能让它们真正发挥作用。
> - 作物再生：`CROP_REGEN_DAYS = 3`（`wbalance.js:688`）野外作物采集后 3 天再生。
>
> **设计总原则**：
> 1. **每种食物必须有取舍**，不能只是"回复数字大小不同"。取舍维度：
>    饱食 / 水分 / 生命 / 疾病风险 / 保质 / 重量（背包格）/ 获取难度。
> 2. **复用已有疾病与天赋系统**，不新造一套 buff 框架。
> 3. **向后兼容**：旧档满背包的 `'food'` 必须继续可吃、不报错。

### F1 食物属性框架 ⬜（**食物系统的第一步，必须先做**）

**状态** ⬜ ｜ **规模** M ｜ **触及红线** §4 序列化（新物品 id 批量）+ §13.1 数值收口

**设计方案**

1. **新增统一食物表 `FOOD_INFO`**（进 `wbalance.js`，§13.1 数值唯一收口）。
   每条食物的**完整属性维度**（这是框架的核心，一次定对）：

   | 属性 | 含义 | 说明 |
   |---|---|---|
   | `satiate` | 饱食回复 | 现有维度 |
   | `hydrate` | 水分回复 | 可为负（如咸/干food 反而耗水）|
   | `heal` | 生命回复 | 现有维度，多数食物应为 0 |
   | `sickRisk` | 疾病风险 | `{ poison: 0.15 }` 形式，直接喂给现有 `SICKNESS` |
   | `sickCure` | 疾病缓解 | 少数食物可缓解（如热食缓解感冒）|
   | `raw` | 是否生食 | 生食风险高、烹饪后转为熟食 id |
   | `keep` | 保质档 | 耐储 / 普通 / 易腐（F4 用，F1 只存字段）|
   | `stack` | 堆叠上限 | 体积概念，肉类堆叠少、干粮堆叠多 |
   | `char` / `color` / `name` / `desc` | 表现与文案 | §13.5 文案收口 |

2. **首批食物清单（分五类，共约 16 种）**——**数量刻意控制**，
   宁少而有区分度，也不要 40 种数值微差的食物：

   | 类别 | 食物 | 设计取舍 |
   |---|---|---|
   | 原有兼容 | 食物（通用）、草药 | 保持现值不变，旧档安全 |
   | 作物（F2） | 胡萝卜、玉米、土豆 | 见 F2 |

### F2 作物差异化与种植闭环 ⬜（原 B1）

代码印证：`wwordcraft-rules.js:96-98` 三配方 `outputId` 全是 `'food'`。
玩家花字块 + 字楔具现出"胡萝卜"，得到的是一堆通用食物 —— **具现系统的成就感在最后一步泄掉**。

3. **与野外作物再生联动**：已有 `CROP_REGEN_DAYS = 3`，野生作物采集后 3 天再生 ——
   三作物的野生版本应遵循同一机制，人工种植周期与之区分（人工更快但要水与肥）。
4. **序列化**：3 食物 id + 3 种子 id 进白名单与迁移表；旧档 `food` 不做反向拆分。

**验收标准**：三作物食用效果各异、种子可种可收、旧档正常、联机一致。

   按感染阶段把**部分身体像素替换为笔画像素**（已有侵蚀渲染基础设施可复用，
   文档 §10.2 有完整的"实体材质色 → 侵蚀过渡色 → 最终文字色"三段插值规范）。
3. **闪烁与错位**：只用于感染 / 不稳定状态、不覆盖全角色、不长时间高频（§10.4 硬约束）；
   必须响应 A4 的两个低动态开关（**A4 应先行或同期**）。
4. **缓存 key**（§13.8 硬性）：感染阶段是新的外观维度，必须加入 `render.js` 离屏缓存 key，
   否则脏读旧缓存 → 颜色错乱。
5. **性能**：感染动画不得逐帧重绘整体 —— 按阶段缓存，阶段变化时才失效。

**验收标准**
- 0~5 阶段视觉可辨识、与能力损失对应（§10.4：身体缺损需与能力损失对应）。
- 缓存 key 含感染阶段，切换阶段无残影 / 错色。
- 低动态开关生效时动画降级、感染进度仍可读。
- 帧率无回归（CDP 61fps 零长帧）。

**验证命令** `_cdp-perf.mjs` + 截图逐阶段人工确认 + smoke（阶段映射纯函数）
