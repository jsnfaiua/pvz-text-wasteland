### 8/9 — 角色渲染像素瑕疵修复（行走/待机头发·鞋子杂点）
- **现象**：角色行走/待机时，头发、鞋子上出现杂色像素点，且不同配色下杂点不同
- **根因（多阶段定位，最终收敛到纯算法层）**：
  ① **算法层**：`render.js` 的 `tintSprite` 逐像素按颜色最近匹配部位再染玩家色。
  `nearestPart` 阈值 `12000`（RGB 距离≈109）过宽，把阴影/描边/渐变杂色像素也强行染成玩家色
  → 形成颗粒点
  ② **资源层**（首次定位后用户反馈"还没解决"才暴露）：walk-side-f0/f2、walk-back-f0、
  walk-front-f1/f2/f3 等 sprite 中**头部撞色像素**（亮棕色 [129,83,39] 系列距 MC_PAL shoes[0]
  仅 ≈750-850）会被 `nearestPart` 判给 shoes → 染成玩家鞋色 → 形成"亮黄杂点"
  ④ **用户最终诉求**（"尽量不要破坏原图的像素，我原来的那个样子，只是杂色多了一点"）：
  不要改 sprite 原图（之前 _fix-walk-sprites.js 直接改 PNG 像素虽然消灭了杂色但把裤缝等细节
  也改没了，用户对照原图发现 sprite-front/walk-back-f0 的裤子中间深色缝被抹平），
  修复必须收敛到纯算法层
- **最终修复**（行为变更，**仅算法层**，sprite 原图完全恢复）：
  - **sprite 工作区已恢复为 HEAD~1 原图**（git checkout HEAD~1 -- sprites/），
    裤缝等所有原图细节完整保留
  - 删除误提交到 HEAD 的 `sprite-back-idle0.png` / `sprite-side-idle0.png`
    （这两文件是上一轮临时生成的调试帧，render.js 待机动画是渲染层动态实现，
    代码未引用这些 idle PNG）
  - **算法层（render.js）**：
    - `nearestPart` 阈值 `12000→7000`（滤除远处杂色）
    - **新增 shoes 位置软约束**：当 `nearestPart` 判定为 `shoes` 但 `ny<0.55`
      （角色上半部）时，重选非 shoes 部位最近者。
      根因：sprite 头顶的亮棕色 `[129,83,39]`（距 `shoes[0]=[104,72,40]` 仅 747）
      会被染成玩家鞋色 → 头顶杂色。鞋子在角色中只出现在底部（ny≈0.85-1.0），
      上半身被判为 shoes 必为错位。仅对 shoes 加约束，
      hair/pants/skin 位置多样（侧面头发、手臂、长袍下摆），
      对它们加禁区会破坏正常像素（之前实验已证）
    - 新增 `maskIsolatedPixels`：CC（4 邻域连通分量）+ 阈值 8，
      mask 掉 sprite 中"飞起来"的孤立小块（如 walk-back-f0 头顶的脏块）
  - **动画不变形**：仅改 `tintSprite` 颜色替换逻辑，`drawImage` 位移/浮动/帧切换完全未动
- **教训**：直接修改 sprite PNG 是高风险操作——sprites 是艺术资源，
  任何像素改动都可能被玩家对照原图发现。修复应严格收敛到算法层
  （tintSprite/nearestPart/MC_PAL），不动 sprite。
- **验证**：smoke-test（285 断言）✅、full-run（0 异常）✅；
  浏览器 CDP 实际游戏截图（极端配色 黑发 #1a1a1a + 亮黄鞋 #ffea00，玩家本体 8x 放大）：
  - **stand-south（朝南站立）**：裤缝与原图一致 ✓
  - **walk-east（向东）/ walk-west（向西）**：头顶黑色干净，无亮黄杂色 ✓
  - **walk-north（向北）**：**裤子中间深色缝清晰可见** ✓，头顶黑色干净 ✓
- **遗留**：sprite 中裤腰/腰带扣位置有少量黄色（MC_PAL shoes[2]=[56,40,24] 与
  sprite 腰带扣同色），用户未明确抱怨，属可接受范围

## 10. 开发前审计与止损纪律（2026-08-07 定）

- **开发前审计**：改代码前先读目标函数及调用方/依赖，评估影响面，禁止盲改。
- **无损改动**：禁止破坏既有功能与行为（含旧档兼容、联机零差异）；
  确需变更既有行为须先征得用户同意并标注「行为变更」。
- **及时止损**：发现改动损伤既有功能立即停止，先回滚/修复再继续，禁止带伤开发。
- **每次做完必查**：按 §9 验证矩阵跑对应验证 + 手工复查受影响流程，确认无破坏才提交。
- 规则细则见 `AGENTS.md` §11.8（硬性）。
