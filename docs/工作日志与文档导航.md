### 8/9 — 角色渲染像素瑕疵修复（行走/待机头发·鞋子杂点）

### 8/9 增补 5 — MC_PAL 重匹配 + 裤腿杂色根除 + shoes 位置硬约束

**用户最终诉求（2026-08-09 多次反馈综合）**：
- "在原图的基础上，因为有杂色嘛，删除减或者减少杂色就可以了。不要将原图给篡改"
- "不管用什么颜色都不要出现杂色，但绝对要保证原图的基础上，原图可以替换颜色"
- "原图可以替换颜色，就是不同的颜色的原图可以上色"

**根因**
- `MC_PAL` 的颜色从旧 sprite 提取，与用户新素材严重不匹配：
  - shirt MC_PAL `[40,80,40]`（中绿），新素材 shirt `[18,43,26]`（深绿）
  - shoes MC_PAL `[104,72,40]`，新素材 shoes `[109,66,32]`、`[39,25,15]`
- 新 sprite 散布在裤子/衣上的**棕色杂色像素**（sprite 设计层的脏像素）距离 MC_PAL.shoes 很近 →
  被判给 shoes → 染成玩家鞋色 → 出现"裤子上闪棕色杂色"（用户反馈）
- "鞋底变黑"是 hair 主色 [55,36,21] 与鞋底暗棕 [39,25,15] 接近导致

**修复（保留原图不动，只改进算法）**
1. **MC_PAL 从用户素材实测重提取**：skin/hair/shirt/pants/shoes 全部用新素材实测主色
   （用户 2026-08-09 提供的 sprite-front/side/back + walk 帧的像素分析）
2. **新增 `nearestPalRef(r,g,b)`**：返回像素最近匹配的 MC_PAL 参考色，作为亮度缩放基准
   替代原 `MC_PAL[part][0]` 固定基准——保留原图明暗层次
3. **nearestPart shoes 位置硬约束**：`if (best === 'shoes' && ny < 0.78) return null`
   非鞋区的棕色像素不染色（保留原色 = sprite 设计杂色），消除"裤子上闪鞋色"
4. **nearestPart 底部 hair→shoes**：`if (best === 'hair' && ny > 0.80) return 'shoes'`
   鞋底暗棕变体不被判给头发
5. **保留 `maskIsolatedPixels`**：mask孤立小块（<4像素），但不动 fixByNeighborhood（已撤掉）

**验证**
- smoke-test 285 通过
- CDP 按 d/a/s/w 真实行走截图：所有方向都干净，无裤腿棕色杂色，鞋子棕色+深色鞋底

**遗留**
- 用户素材的 sprite 中确有散布的棕色像素（sprite 设计层），算法层不染色处理，
  但这些原色保留后在不同配色下可能略有视觉痕迹（非染色的"原色小点"），属用户素材层
- `walk-back 4 帧`（朝北走路）仍未替换

**教训**：核心问题不是 tint 算法，而是 MC_PAL 颜色与用户素材不匹配。
更新 MC_PAL 匹配实际素材后，基础判定就准确了，再加精确的位置约束就能根除杂色。

## 7. 预览资源清理制度（2026-08-07 定）

- 开发中生成的预览资源（CDP 截图 `_cdp-*.png` / `_qa_tmp/` 临时文件 / 临时预览页）
  在**预览验收完成后定期清理**，至少每个功能迭代结束 / 提交前清一次。
- 仅保留三类：① docs/ 设计文档引用的图；② 标注为回归基线的对照素材；
  ③ 用户明确要求保留的效果图。
- 规则细则见 `AGENTS.md` §13.12（硬性）。

## 8. 代码行数统计与冗余清理制度（2026-08-07 定）

- **每次功能迭代完成必须统计代码行数**：`node dev-tools/count-lines.mjs`
  （总行数 + 按模块分布，mod-wasteland 按文件明细）。
- **基线（2026-08-07）**：总计 **32,099 行 / 58 文件**；mod-wasteland 21,615 行（30 文件），
  其中 render.js 4,298 / survival.js 4,177 / wnpc.js 1,597 / world.js 1,159 / wvehicle.js 1,095。
- 按功能评估行数增量，异常增长排查冗余；删除冗余须：确认无引用 → 全量回归验证 →
  游戏运行与全部功能不受影响才可提交。
- 规则细则见 `AGENTS.md` §13.13（硬性）。

## 9. 开发者模式制度（2026-08-07 定）

- **所有新功能必须提供开发者模式测试入口**（局内 F9 面板 `wdev.js` / `saveData.devMode`）：
  属性/物品/召唤/状态/时间等至少一类，无需走完整自然流程即可直接验证。
- **开发者模式对任何玩家开放**（单机 / 联机 host / 联机 guest，无权限门槛）；
  联机属性类 `devflags` 上报回传、召唤类 `devcmd` host 权威执行（双端可见）。
- 规则细则见 `AGENTS.md` §13.14（硬性）。

## 10. 开发前审计与止损纪律（2026-08-07 定）

- **开发前审计**：改代码前先读目标函数及调用方/依赖，评估影响面，禁止盲改。
- **无损改动**：禁止破坏既有功能与行为（含旧档兼容、联机零差异）；
  确需变更既有行为须先征得用户同意并标注「行为变更」。
- **及时止损**：发现改动损伤既有功能立即停止，先回滚/修复再继续，禁止带伤开发。
- **每次做完必查**：按 §9 验证矩阵跑对应验证 + 手工复查受影响流程，确认无破坏才提交。
- 规则细则见 `AGENTS.md` §11.8（硬性）。
